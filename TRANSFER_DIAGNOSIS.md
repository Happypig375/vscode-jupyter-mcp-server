# File-transfer diagnosis, 12 October 2026

This source repair was developed against version 0.4.1 without installing or reloading the extension, accessing the active VS Code/Colab session, or transferring research files. The reported large Colab upload/runtime failures were not reproduced remotely. Source defects and synthetic regressions do not establish the cause of those crashes.

## Confirmed mechanism

Both directions use the public Jupyter `executeCode` API, rather than Colab's native file-transfer implementation. Upload initializes a random remote temporary file, executes one base64 append per 256 KiB chunk, then rereads the remote file for SHA-256 verification and promotes it atomically. Every append opens/closes the file and performs `flush`/`fsync`. Download reads metadata, executes one base64 output per chunk, then independently hashes the remote source before promoting a local temporary file. Existing no-overwrite and checksum requirements remain.

For a 62,572,000-byte file, either direction normally requires 239 chunk calls plus two bookkeeping calls: 241 API calls. Upload base64-encodes the chunk, the JSON arguments containing that chunk, and the Python source containing those arguments. The synthetic large-file regression measured a maximum code payload of 622,343 bytes (about 608 KiB). A full download chunk produces about 349,528 characters of base64 data, plus receipt metadata. Neither direction uses a single native upload/download request. The previously recorded live 524,425-byte round trip does not validate this large-file workload.

Before this repair, awaiting either `executeCode` or its output iterator had no deadline. Signalling cancellation did not bound the await. Upload's attempted cleanup could stall in the same way. The broker's generic peer request deadline is approximately 24.8 days, so it is not a useful fallback for this defect. These facts explain how a request can remain pending after a kernel becomes unavailable; they do not explain why a Colab runtime died.

Microsoft's [public API declaration](https://github.com/microsoft/vscode-jupyter/blob/main/src/api.d.ts), checked on 12 October 2026, defines completion through an async output iterable, accepts a cancellation token, exposes kernel status events, and returns already-started kernels for open notebooks. These API executions do not affect notebook execution count/history. The current [wrapper implementation](https://github.com/microsoft/vscode-jupyter/blob/main/src/standalone/api/kernels/index.ts) caches one public object per underlying kernel and extension. This supports object-identity revalidation, while an observed restart must also invalidate an operation that retains the same wrapper.

## Repair and limits

Each initial kernel lookup and each subsequent execution, including revalidation and waiting for stream completion, has a 60-second deadline. Receipts are capped at 528,384 characters, above the current full-chunk response size. Cancellation or an unavailable status can terminate the local wait earlier. Pending promises and iterator `return()` are observed without blocking the caller or exposing raw kernel error output.

One transfer at a time may own a target notebook or kernel. Every execution rechecks the original active idle Python kernel. A different kernel or any observed non-idle/non-busy lifecycle state ends the transfer; cleanup cannot run against a replacement. If a dispatched operation has not finished, the original kernel is quarantined until its pending execution/read and iterator closure settle. A replacement object is permitted for a later operation. A same-object restart does not bypass quarantine. A provider that never settles may require an extension reload to clear that local quarantine; this repair does not initiate one.

Remote cleanup is attempted only after a settled failure, on the same idle kernel, with a five-second deadline. No cleanup is queued behind unfinished code. A random remote `.part` file can remain. Upload reports uncertainty if destination promotion was dispatched but confirmation failed. Local filesystem failures and races with user work remain possible; the public API offers no atomic reservation against user execution. The deadlines are per execution, not a whole-file deadline, and slow but progressing large transfers may take many minutes.

MCP request cancellation/connection loss is not forwarded through the existing server/router/peer protocol. The internal token path is tested, while production uses deadlines and status observation independently of the client. Adding a cross-window cancellation protocol is separate work. Chunk size and transport are unchanged: no supported public API payload-size guarantee or large-file live regression justifies increasing payloads. The cost of repeated round trips and fsyncs remains an efficiency issue for future evaluation.

## 13 October continuation: move large payloads out of kernel execution

The repaired 0.4.2 was active when a subsequent 65,568,700-byte Colab upload failed after 314.17 seconds with `kernel became unavailable`, before destination commit. The selected runtime had answered a probe first. Jupyter then removed the Colab controllers and received HTTP 404 responses; Colab showed its generic server-removal warning. Neither the logs nor this patch establish why the server disappeared. A second bundle request immediately found no active kernel. Neither upload was verified; the earlier failures remain evidence, not successful retries.

Readback confirmed the live MCP advertised 0.4.2 and the installed bundle matched the repaired build (SHA-256 `b308253ee8694863a47786b9e78a6d438e4bdaa87a99b133b9e6cdfba4f3ceda`). The earlier timeout repair did not remove large payloads from the execution channel. Treating smaller live successes as validation of large-file reliability was too broad.

The installed Colab 0.9.7 bundle implements native upload through `workspace.fs.writeFile` and download through `workspace.fs.readFile`, using its registered `colab` filesystem. The corresponding public [filesystem implementation](https://github.com/googlecolab/colab-vscode/blob/b3598086628f2d834de882a151c94d4d25f25849/src/jupyter/contents/file-system.ts) uses Jupyter Contents REST operations. This is a distinct transport from public kernel execution. Colab owns credentials and connection refresh; this extension does not read them or invoke private provider objects.

Version 0.4.3 uses that file service for files above 4 MiB and for explicit `colabFileUri` requests. It discovers only mounted/open Colab URI roots, or validates the supplied URI against the exact kernel path. A fresh nonce file in the selected kernel's `/content` must be readable from the single candidate before any payload I/O. Multiple exposed roots require an explicit URI; no sequential root probing occurs. A mismatched or unavailable route fails; there is no large kernel fallback. Generic small transfers remain supported. The 4 MiB cutoff is a conservative workload limit, not a measured Colab safety threshold.

An upload uses two short kernel executions (nonce/temp initialization, then checksum and atomic promotion) around one native filesystem write. A download uses three (source size, nonce, independent source checksum) around one native payload read. The old 65.6 MB path would require 251 chunk executions in each direction plus bookkeeping. No-overwrite and byte/hash requirements remain. Native payload I/O has a two-minute wait bound and is quarantined until its uncancellable promise settles; a timeout can leave random temporary files. These waits do not prove the provider stopped or determine an uncertain final promotion. Native operations buffer the whole file and therefore have a hard 64 MiB limit; changes to the source during a provider read can still increase transient memory before the returned size is checked.

Local validation includes a synthetic 65,568,700-byte round trip and a separate real-Python/real-file fixture using the production adapter with a local implementation of `workspace.fs`. The latter executes the generated Python commands with only argument paths mapped into its isolated test directory. It checks actual hashes, empty files, explicit and discovered roots, wrong URIs, corruption, atomic no-overwrite and overwrites. Its largest generated kernel request was 1,503 bytes. Fault fixtures cover wrong/ambiguous runtime binding, kernel replacement, native request timeout and quarantine, with the earlier kernel lifecycle regressions retained. These are software checks; the native Colab network route and runtime survival remain unverified until a live round trip completes.

The independent Opus review found that the first nonce filename began with a dot, which default [Jupyter Contents settings](https://jupyter-server.readthedocs.io/en/latest/other/full-config.html#ContentsManager.allow_hidden) can hide. The corrected nonce name has no leading dot, and the real-file fixture now enforces hidden-file rejection. Binding reads have a separate fifteen-second deadline and do not quarantine the selected kernel because they are small read-only operations, possibly against a stale root. Multiple roots require explicit selection. Busy-kernel errors remain distinct from a nonce mismatch. Added fault fixtures exercise stale roots, native cancellation and unavailable-status events. CI explicitly provisions Python 3.12. Full local MCP integration again stopped at the pre-existing empty-window handshake deadline; this does not invalidate the passing focused checks or supply a full-suite pass.

## 16 October: kernel-route memory growth and the 0.4.4 fix

**Observed.** With 0.4.3 active, two Colab runtimes were lost while files at or below 4 MiB were uploaded through the kernel route (several 3.5 MB pieces of larger inputs, so the 4 MiB guard was bypassed by the caller). Both losses came after roughly 35-45 MB of payload, about 90-150 MB of request code, within a few minutes. Kernel memory rose from 1.1 GB to 1.6 GB after about 35 MB had been uploaded. The 13 October loss of a 65.6 MB kernel-route upload fits the same pattern. The cause of the server removal itself is still not directly observed.

**Mechanism found.** IPython stores the source of every executed request in `linecache` for the lifetime of the kernel, also for executions outside history, so tracebacks can show code. IPython 7 additionally keeps it in `linecache._ipython_cache`. Version 0.4.3 encoded each 256 KiB chunk three times (base64 chunk inside JSON, base64 of the arguments inside the source, base64 of the source inside the request), about 622 KB per request, all of which stayed cached. Reproduced locally with IPython 8.24.0 and 9.16.1 (12.4 MB retained after 20 chunks) and on the live Colab kernel, IPython 7.34.0 / ipykernel 6.17.1 (24.87 MB reported after 20 chunks; that IPython lists each entry in both caches, so this may count the same objects twice). Downloads put almost nothing into their request code, so they do not grow this cache. Their base64 receipts still pass through the kernel's output channel, about 1.33x the bytes, which counts towards the same overall traffic.

**Fix (0.4.4).**
- Every transfer request starts with `# jupyter-mcp-transfer` and, before running its command, removes earlier tagged sources from `linecache.cache` and `linecache._ipython_cache`. This includes its own entry, which IPython adds before execution. A replay through a real IPython shell now retains 0 bytes, both in the local real-Python regression (16 real requests) and on the live Colab kernel (20 requests, 0.0 MB).
- Upload payloads appear once as a base64 literal in the request's namespace (about 1.33x, not 2.4x). Chunks are zlib-compressed in both directions when that saves at least 10%, so CSV-like requests shrink about twelvefold.
- A kernel object carries at most 64 MiB of chunk traffic: request code for uploads, base64 receipts for downloads. Further chunk transfers are refused before dispatch, with guidance to use the native Colab file service or restart the kernel.
- Kernel exceptions return an error receipt naming only the exception class (for example `FileNotFoundError` for a missing destination directory). File contents and messages are not included.

**Checks.** `npm run typecheck`, `npm run compile`, `npm run compile:test`, the synthetic suite (new tests cover compressed and incompressible chunks, the purge tag in every request, the absence of nested payloads, error receipts with cleanup, and refusal at the budget with a fresh budget for a new kernel object), and the real-Python suite (native 65.6 MB round trip, a new 1.42 MB kernel-route round trip whose largest request was 351,340 bytes, and the IPython replay). CI now installs IPython so the replay runs there instead of being skipped.

**Limits.** The purge removes only tagged transfer sources. The 64 MiB budget is a conservative guard, not a measured Colab threshold. Native transfers remain the right route for large files and still need a mounted or opened Colab root.
